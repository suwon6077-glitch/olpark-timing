# 올팍 타이밍 (올림픽공원 출차 타이밍 안내)

공연이 끝난 뒤 올림픽공원 주차장에서 **어느 출구로, 언제 나가야 덜 기다리는지** 알려주는 웹 서비스입니다.
한국체육산업개발(주)의 입출차 기록과 공연·날씨 연계 데이터를 분석하고, **랜덤포레스트 분류 모델**로 동2·남2·북2문의 30분 단위 혼잡 등급(원활·보통·혼잡)을 예측해 출구 추천에 씁니다.

- 웹: https://suwon6077-glitch.github.io/olpark-timing/
- 2026 한국체육산업개발(주) 공공데이터 활용 경진대회 출품작

## 화면

| 출차 경로 | 공연 일정 |
|---|---|
| 주차장을 고르면 공원 내부 도로로 동2·남2·북2문까지의 경로, 이동 시간과 예상 대기를 더해 가장 빠른 출구를 추천합니다. 3D 항공사진 지도와 내비 보기를 지원합니다. | 지난 공연(연계 데이터)과 다가오는 공연(올림픽공원 홈페이지)을 날짜별로 보여줍니다. 다가오는 공연을 누르면 **출구별 혼잡 예측표**가 나오고 대기값이 예측으로 바뀝니다. |

## 자동 갱신

| 워크플로 | 주기 | 하는 일 |
|---|---|---|
| 실시간 주차대수 수집 | 5분마다 | 기관 실시간 주차현황 API → `data/realtime_parking.csv` |
| 공연 일정 갱신 | 매일 03:00 | 연계 데이터 → 지난 공연, 홈페이지 → 다가오는 공연, 랜덤포레스트 → `docs/congestion.json` |
| 입출차 전체 수집 | 수동 | 입출차 241만 건을 이어받기 방식으로 수집 (Artifacts로 보관) |
| 연계 데이터 수집 | 수동 | 연계 데이터 원자료 |

API 키는 저장소 Secrets(`KCISA_KEY`, `LINKED_KEY`, 선택 `KOPIS_KEY`)에 두며 코드에는 없습니다.

## 랜덤포레스트 출구 혼잡 분류

- **분류 대상**: 출구 3곳 × 저녁 17~24시 30분 구간. 그 30분 중 가장 붐빈 10분의 출차 대수 ÷ 출구 10분 처리 능력(약 85대)이 50% 미만이면 원활, 50~85% 보통, 85% 이상 혼잡.
- **학습 데이터**: 2025년 1~7월 출차 기록 150만 건 → 212일 × 3출구 × 14구간 = 8,904구간 (원활 76.6%, 보통 18.5%, 혼잡 4.9%).
- **모델**: scikit-learn RandomForestClassifier, 나무 300그루, 깊이 14, 잎 최소 3, 분기 변수 50%, `class_weight='balanced_subsample'`. 하이퍼파라미터는 날짜 단위 중첩 교차검증으로 선택.
- **검증**: 날짜 단위·주 단위 5겹 교차검증과 시간 순 검증(1~5월 학습 → 6~7월 예측).

| 모델 | 매크로 F1 | 혼잡 F1 |
|---|---|---|
| 다수 등급(항상 원활) | 0.289 | 0 |
| 로지스틱 회귀 | 0.512 | 0.285 |
| 의사결정나무 | 0.570 | 0.375 |
| 랜덤포레스트 (직전 주차대수 포함) | **0.694** | **0.503** |
| 랜덤포레스트 사전 예측 (웹에서 사용, 공연 전 정보만) | 0.609 | 0.403 |

웹은 공연 전에 알 수 있는 정보(출구, 시각, 공연 시작·종료 시각, 예상 관람객, 공연 수, 요일, 주말·공휴일)만 쓰는 사전 예측 모델을 씁니다. 시간 순 검증에서 매크로 F1 0.627로 단순 기준(0.462)보다 높았습니다. 예상 대기는 등급별 대기(원활 1분, 보통 5분, 혼잡 13분, 출구 포화 시간의 절반)를 확률로 가중해 구합니다.

## 분석 재현

1. Actions의 "입출차 전체 수집"으로 입출차 원자료를 받고 `olpark_preprocess.py`로 정리합니다. 원자료는 용량 때문에 저장소에 두지 않습니다.
2. `analysis/rf_build.py` → `rf_final.py` → `rf_advance_eval.py` 순서로 실행합니다.
3. 학습 표 `analysis/rf_train.csv`만 있으면 `predict_congestion.py`는 바로 돌아갑니다.
